Performance teardown Qwen2.5-14B · A100 80GB CRIU 4.2.1

How we cut GPU cold start from 11 minutes to 39 seconds

Restoring a 52 GiB checkpointed vLLM engine used to take 677 seconds. It now takes 39. Two thirds of that came from configuration mistakes, not from the kernel patches we set out to write — and the patches themselves delivered about a ninth of what we predicted.

What "cold start" means here, precisely

Snapshot-and-restore promises a large language model server that skips initialization: instead of loading weights, compiling kernels and capturing CUDA graphs on every scale-up, you restore a process image of a server that already did all of that. The promise is real. The delivery is an I/O problem wearing a GPU costume.

Every number on this page is end-to-end: from the moment the restore request is created to the moment the pod reports Ready — pod scheduling, artifact transport, runc restore, and GPU resume, all of it. Not "CRIU restore only", which is the flattering subset. Where we quote the CRIU phase alone, it is labelled.

Every row was verified by generation, not by readiness probe. A pod that answers its health check but produces garbage tokens has not been restored, it has been resurrected badly. The prompt was "The capital of France is" and the answer had to be Paris.

01

Snapshot the right moment, not the current moment

Before any of the speed work: we were checkpointing a live serving process, which means checkpointing whatever it happened to be holding. An io_uring ring CRIU cannot dump. A listening socket with live peers. NCCL registrations. And a KV cache full of nothing useful.

The fix is a quiesce protocol, and it is a correctness change that happens to also be a size change. An entrypoint shim initializes the engine, releases KV physical memory, touches /snapshot/ready-for-checkpoint, then blocks in a poll loop. The checkpoint happens while it sits there. On restore, execution resumes at the exact instruction inside that loop, the rendezvous file is now present, KV pages are remapped, and only then does the HTTP frontend start.

That ordering is the whole trick. Everything un-dumpable — the event loop, the TCP listener, the distributed runtime — is created after the quiesce point, so it never exists in the image. It gets built fresh on the restore side, on a node where it can be built correctly.

Five things a real engine did that broke the dump

The quiesce point buys control over what is created after it, and nothing at all over what engine initialization already did. All five of these existed by the time weights finished loading:

  • NVML keeps its own /dev/nvidiactl handle. cuda-checkpoint returns the descriptors the CUDA runtime owns; NVML's is not one of them. Any library calling nvmlInit without a matching shutdown — PyTorch's device-count probe does — leaves one behind, and CRIU refuses the dump.
  • fork spreads it. vLLM runs EngineCore in its own process and defaults to forking, so the worker inherits the parent's nvidiactl descriptor. In the child it belongs to no library, so nothing releases it.
  • Anything bound to the pod IP. ZMQ endpoints and the torch.distributed TCPStore are created during engine init, before the quiesce point, so deferring the frontend does not help. They must be on loopback, which exists identically in every pod.
  • Deleted-but-mapped files on /dev/shm. glibc's sem_open leaves every POSIX semaphore mapped from an unlinked path. CRIU demands link-remap, which needs a link back at restore that a fresh pod's tmpfs cannot provide. Drop the last link before the dump and CRIU writes a ghost file instead, contents and all.
  • /dev/shm is not in the image at all. It is a pod-scoped external mount, captured separately and laid back down over the restored pod's tmpfs.
02

Ship a directory, not a tarball

runc restore --image-path takes a directory. We were handing it one — after materializing it from a tar, because the kubelet checkpoint API returns a tar. So every restore paid an untar of the full artifact before CRIU read a single byte.

Writing CRIU images straight to a directory and syncing the directory deletes that step outright, and it is the precondition for everything downstream: per-file objects are what make parallel prefetch possible at all. A manifest written last acts as the commit marker, so a reader that ignores an uncommitted prefix never sees a torn tree.

That is the read side. The write side is where the tar costs the most, and it is easy to miss because the number never appears in a restore trace. The kubelet checkpoint API has no directory mode, so publishing one artifact writes its bytes three times: CRIU writes the images, the kubelet reads them back and writes the archive, and the agent reads the archive back and expands it into the layout a restore can actually use.

We measured it as a controlled A/B — same node, same model, same afternoon, with the only variable being who runs the dump. /proc/diskstats sampled every five seconds across the whole build:

The OS disk is the headline: 257.9 GB down to 0.1 GB. That quarter-terabyte was the tar, staged on /dev/root because that is where /var/lib/kubelet lives, then read back to be expanded. The build was spending most of its I/O writing a temporary file to the slowest device on the node, to produce an artifact bound for the NVMe tier all along.

The nvme0n1 write column looks worse for the agent until you split it by phase. 27.3 GB lands before the dump even starts, while the engine loads weights — that is in both columns and has nothing to do with checkpointing. The dump itself writes 56.5 GB to produce a 56.5 GB artifact: a write amplification of exactly 1.0, which is the floor. The kubelet column only reaches a lower NVMe figure by pushing the difference onto the OS disk, four times over.

A trap worth naming Our artifact store is a FUSE mount, and on it rename copies without unlinking the source. Every artifact on the cluster had a full-size .part file beside it, silently doubling storage since v1 shipped. Separately, O_TRUNC is ignored there — re-uploading a revision left shrunken files carrying the previous tail. And rmdir on a non-empty directory returns 0 without unlinking anything, which is enough to make Go's os.RemoveAll report success over a tree it never touched: it tries a plain Remove first and returns early when that "succeeds". We found that one seventeen minutes into a 56 GB dump, when CRIU refused to overwrite a descriptors.json an hour older than the run. An artifact store is not a POSIX filesystem just because it is mounted like one — and on one that isn't, a return value is not evidence. Read it back.
03

The bytes were going to the wrong disk

This is the part worth stealing, and it is the least glamorous. After halving CRIU restore with real kernel work, we sat at 452 s end-to-end for a 52 GiB artifact. That is roughly 0.25 GB/s sustained. PCIe on this node moves that in about three seconds.

So the patched CRIU was no longer the constraint — getting bytes to it was. We had three hypotheses. Sampling /proc/diskstats per device across a restore found the answer, and it was none of them: 

# sectors read, per device, during one staging restore
sda        266 MB/s    ← the 256 GB OS disk
nvme0n1      0 B/s     ← the 894 GB local NVMe

A pre-warm step was copying the artifact off the mount onto "node-local storage" and CRIU was reading that copy back. The copy was landing on the OS disk. The fast device was not being touched at all. Deleting the copy — one config flag — moved reads onto the NVMe and took end-to-end from 452 s to 253 s.

Then the second half. With staging gone, we measured the same bytes two ways: through the FUSE mount, 500–690 MB/s; straight off nvme0n1, 2.6 GB/s single-stream and 4.5 GB/s at four streams. The client already promotes everything it serves onto a node-local cache tier laid out as a 1:1 mirror of the artifact. The bytes were already on the fast device. Reading them back through the userspace filesystem that put them there was pure tax.

When the manifest check confirms every file is resident at the stated size, we point --image-path at the cache tier and the mount leaves the read path. A partial mirror declines and falls back; a size that disagrees with the manifest is an error rather than a silently wrong restore.

There was a third finding in the same sweep. Prefetch concurrency was pinned at 2, and read throughput actually peaks at 4 (~1.3 GB/s), falling on both sides — 542 MB/s at 2, 642 MB/s at 8. The 2 had not been chosen for speed. It was chosen because 8 had OOM-killed the client, so a workaround for a memory bug had quietly become a throughput ceiling. Those are the most expensive constants in any system: the ones that were right once.

04

Six patches to CRIU's restore read path

Stock CRIU restores memory single-threaded and synchronously: read a page image, map it, move to the next. For a 52 GiB image on a device that wants deep queues and many streams, that is the wrong shape of I/O. We forked CRIU 4.2.1 and landed six commits.

Fork branch, based directly on the v4.2.1 tag
#CommitTouches
0001make shared restore state thread-safebfd.c, log.c
0002read pages through native AIOpagemap.c
0003restore shmem segments in parallelshmem.c, mem.c
0004restore memfd inodes in parallelmemfd.c
0005read memfd and shmem pages asynchronouslyshmem.c
0006bound how far one async read coalescespagemap.c

Patches 3 and 4 are the ones that halved CRIU restore, 445 s to 225 s. Patches 5 and 6 are a late and slightly embarrassing fix: we had written a native AIO path in patch 2, wired a queue-depth knob to it, and shipped it — and it was dead code for the bytes that matter. The shmem restore call passed flags 0, so the async path was unreachable on 205 of 208 page images. The depth knob had been connected to nothing the entire time. The A/B test that "proved" AIO did not help had been comparing a build against itself.

Patch 6 is inseparable from patch 5. Without a cap, the pagemap layer coalesces each memfd into one enormous read, the queue never holds more than a job or two, and depth is meaningless. We proved that on hardware rather than asserting it, by running the unbounded case as a control:

Where the prediction broke

We forecast that putting memfd bytes on the async path would take the read phase from 8.9 s to roughly 3 s. Here is what it actually did, at a fixed 8 threads, cold, on the same node:

Predicted
8.9 s → ~3 s

Measured
21.4 s → 19.4 s
About 2 s of improvement. Roughly a ninth of the forecast.

Three things the arithmetic missed, in order of how much they mattered:

  • Depth saturates at 16. Depths 16 and 128 are indistinguishable — 19.4 s both. Four extra doublings of queue depth touch nothing, so past 16 the constraint is not submission depth. The obvious suspect was the coalescing cap starving the queue; the sweep above rules it out, since 256 KiB and 1 MiB tie.
  • Threads stop helping, then start hurting. At depth 1, going from 8 to 24 threads made it slower: 21.4 s to 23.9 s, 24 serial streams contending where 8 sufficed. At depth 128 the same change is worth 0.3 s, inside noise.
  • The read path was never 21 seconds of reading. 56.4 GB in 19.4 s is 2.9 GB/s — already past the device's single-stream figure. The remainder is CRIU's own per-object work across 205 memfds: create, map, fill, unmap. The device stopped being the limit; the arrival rate of work to give it became the limit.
What the model got right and wrong The submission-depth theory was correct about the mechanism and wrong about the headroom. It was still worth building — 2 s is real and the O_DIRECT result (12,575 of 12,575 submissions) retired a standing question about alignment. But the honest summary is that the read path is close to done, and we would have learned that a week earlier by measuring the device ceiling before writing the patch.

The floor we cannot reach from here

The best cold run is 39 s, and it splits cleanly: 19.4 s of CRIU and 12.5 s of GPU resume. That second number is a single gap in the log between cuda_plugin: resuming devices and the next line — one cuda-checkpoint call, inside NVIDIA's plugin, with no I/O of ours in it.

It held to a tenth of a second across all nine tuning configurations we ran. Queue depth, thread count, chunk size, direct I/O: none of them moved it by a measurable amount. That is the cleanest possible evidence that read-path work cannot reach it, and it is why we stopped.

What remains is structural. The artifact is roughly twice the model weights, because sleep(level=1) offloads weights to host RAM rather than dropping them — so they get captured in the image instead of being re-read from a weight store. Splitting weights out to restore over an independent channel is the one remaining change that plausibly moves the GPU half too, by shrinking what has to be resumed rather than reading it faster.

If you are doing this yourself

The generalizable lesson is not any particular patch. It is that we spent weeks on kernel work worth 35% of the win while two configuration flags worth 65% sat undiagnosed, and only found them by instrumenting per-device throughput. In order of expected value:

  1. 01Measure per-device, not per-process. /proc/diskstats sampled across a restore is what found the wrong-disk bug. Aggregate throughput would never have shown it — the bytes were moving, just to the wrong place.
  2. 02Find the device ceiling before optimizing toward it. Our patch targeted a read path already running at 2.9 GB/s against a 2.6 GB/s single-stream device. Knowing that first would have reordered the work.
  3. 03Drop the page cache, or you are benchmarking memcpy. These nodes hold 216 GB of RAM and the artifact is 52 GiB. Our first AIO A/B was a null result because runs 2 through 4 read zero bytes from any device. Confirm cold with a device counter, not with intent.
  4. 04Run the disabled case as a control. The unbounded-coalescing run is what proved patch 6 is load-bearing. A knob with no control is a knob you are guessing about — as we did for a month with a depth setting wired to dead code.
  5. 05Verify correctness every row. A restore that is fast and wrong is worse than one that is slow. Generate tokens and read them; do not trust the readiness probe.
  6. 06Audit constants that were right once. Prefetch was pinned at 2 to dodge an OOM. The OOM was real. The ceiling outlived the reason, and nobody re-derived it.
